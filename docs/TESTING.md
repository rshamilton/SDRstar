# How SDRstar was tested, and what was not

This page is the honest record. "Verified" means a test or an observation actually showed it; where something could
not be tested here it says so.

## 1. The layers

| Layer | What it proves | Where |
| --- | --- | --- |
| **Core unit and integration tests** (114 test cases, about 58,850 checks, 16 programs) | The planner, rigctl bridge, process handling, signal detection, identification evidence rules, trunk follower, text decoders, resampler, FFT, the voice jitter buffer, and the card preferences (hidden tips, auto-decode rules). The integration tests run the **real DSD-neo, multimon-ng and rtl_433** on recorded signals, with the radio replaced by a simulator. | `core/tests`, run with `ctest` (or `scripts/test_core.sh`) |
| **Real-air trunk following** | The follower, with the real DSD-neo, on a real recorded P25 system, with a simulated RTL-SDR window moved over the recording. | `core/tests/test_real_trunk.cpp` |
| **Sanitizers** | No data races (ThreadSanitizer) and no memory errors (AddressSanitizer / UBSan) in the core. | `scripts/ci_tsan.sh` runs on every push; AddressSanitizer + UBSan + LeakSanitizer were run by hand over the whole suite: no reports |
| **Safety audit** | The safety claims in [SAFETY.md](SAFETY.md) hold in the source. | `scripts/safety_audit.sh`, every push |
| **Whole-GUI tests** | The real SDR++ application with the SDRstar module loaded, running under a virtual display with software OpenGL, fed recorded wideband files through SDR++'s File Source, driven with simulated mouse clicks and screenshotted. | development sandbox (not in CI: CI machines have no OpenGL window server) |
| **Soak tests** | Memory, threads, file descriptors and child processes stay flat over long use. | development sandbox |
| **macOS build checks** | The real `SDRstar.app` for Apple Silicon and Intel builds, references no library outside the bundle, targets macOS 12, is signed, every plug-in loads, the helpers run from a relocated copy, the core tests pass natively on macOS, and a headless launch works. | GitHub Actions (`docs/MAC_BUILD.md`) |

## 2. Recordings used, and how they were vetted

Test recordings were found and validated by a dedicated pass whose rule was "do not trust a sample until it has been
checked": every sample was inspected (spectrum plot looked at, header sanity-checked) and, where a reference decoder
existed, decoded independently. The full catalogue, with source URL, licence, SHA-256 and verification notes for each of
the 73 entries (63 verified, 8 plausible, 2 rejected), is in [`tests/samples/`](../tests/samples/README.md). Highlights:

* **DSD-neo's own fixtures**: 2-second, 48 kHz IQ captures of P25 Phase 1 (C4FM and CQPSK, control and voice), P25 Phase 2,
  DMR Tier III, DMR voice, NXDN, dPMR, D-STAR, YSF, M17, EDACS, ProVoice, analog NFM/AM. Each is already asserted by the
  DSD-neo project's own tests.
* **A real 800 MHz public-safety capture** (HackRF, 20 MS/s, archive.org item `SDR-IQ-20221126`), cut into three
  time-aligned 2.4 MS/s slices (what an RTL-SDR would see) containing a real **P25 Phase 1 control channel (NAC 0x451,
  WACN BEE00, system 0x45C, site 21)**, a second control channel of another system, voice channels and a DMR carrier. The
  decoded channel plan (base 851.00625 MHz, 6.25 kHz steps) matched the carriers within 2 kHz, independently confirming
  the sample rate and centre frequency.
* **A real POCSAG pager IQ recording** (decodes at -10.5 kHz offset) and the pager audio samples from multimon-ng's repository.
* **A real 1 MS/s capture of 433.9 MHz sensors** (Acurite tower sensor id 4700, LaCrosse-TX id 83) and 36 rtl_433_tests
  captures (433 / 868 / 915 MHz) for which rtl_433 reproduces the upstream expected output.
* **Synthetic** AX.25 / APRS and EAS / SAME audio, generated by `tools/gen_afsk_samples.py` from the published
  encodings. These prove the decoder wiring and arguments only, not RF realism, and are labelled that way.

## 3. What each feature was verified with

| --- | --- | --- |

| P25 Phase 1 control-channel identification (C4FM, CQPSK) and trunk detection | DSD-neo fixtures; the real 800 MHz slices | pass: NAC / WACN / System / Site decoded from the air |
| Following a trunked system, hop-out and return, "out of bandwidth" refusal with hop off | simulated radio with DSD-neo fixtures; **real recorded P25** (`test_real_trunk`); full GUI | pass; the real recording's 4 MHz-away grant produced the hop (and its refusal with hop off) |
| P25 Phase 2, DMR, NXDN, dPMR, D-STAR, YSF, M17, ProVoice, EDACS identification | the matching DSD-neo fixtures run against **every** candidate decoder (a full confusion matrix; evidence rules were derived from it; 219 checks) | pass, with two documented weak spots below |
| No false identification on noise / empty channel | noise fixture; empty-channel probe in the full GUI | pass |
| Spectrum detector: finds signals, centre / width, adjacent channels, bursts, no phantom edge signals, DC spike, retune by absolute frequency | 12 unit-test cases on real recordings and synthetic scenes | pass |
| Pager (POCSAG) text decoding | real pager audio **and** real pager IQ through the full GUI | pass (decoded the sample's known test page) |
| ISM sensors (rtl_433) | real sensor captures, including through the full GUI on the 1 MS/s recording | pass (Acurite id 4700, 2.5 C, 58 %, as expected) |
| Aircraft (ADS-B) decoder: demodulator, CRC with single-bit repair, callsign / altitude / CPR position / velocity | the published reference messages from "The 1090 MHz Riddle" (decode to the published callsign, position and velocity); a synthetic modulator with noise, back-to-back frames, odd chunk sizes and injected bit errors; **a real 2 MS/s recording** through the unit test and the full GUI | pass: 145 CRC-verified frames from the one aircraft in the recording, where the reference decoder (dump1090) finds 120; noise alone produces none |
| APRS, EAS | synthetic signals through the real multimon-ng and our resampler | pass (synthetic only; no real APRS/EAS recording was found) |
| Child-process safety: end on host death, kill escalation, bounded writes; background children run at a lower CPU priority | `test_subprocess` | pass (decoder gone 0.02 s after SIGKILL of the host) |
| **Decoded voice is speech at the right speed**: the channel layout of every decode mode, and the audio that reaches the speakers while following | the real DSD-neo on real P25 voice recordings; the pitch of what comes out is measured (human voice, not double); the old stereo assumption was put back temporarily to prove the test fails (median pitch 296 Hz instead of 148 Hz) | pass |
| Voice smoothing (jitter buffer): pre-buffering, short transmissions, underruns, bounded queue, one-slot TDMA calls on both speakers, concurrent producer / consumer | `test_voice_jitter` (injectable clock, no audio hardware) | pass |
| Hidden tips and auto-decode rules (once per cursor visit, never over a running job, quiet after Stop, Identify then decode) | `test_card_prefs`; then in the whole GUI: tick the checkbox, rest the cursor on an identified D-STAR signal (decoding started by itself), Stop (did not restart), move to the identified P25 control channel (following started) | pass |
| FFT (spectrum tap and detector) | `test_dsp_lite`: against a reference DFT for every size, a pure tone, size changes | pass |
| Audio sink never blocks the audio thread (patch 0005) | the patched pull logic compiled against SDR++'s **real ring buffer**: an empty stream returns at once with silence, a started block is completed, an unfinished one gives up after a few ms, stopping cannot be held up; the unpatched read on a silent stream was shown never to return | pass (the freeze itself needs CoreAudio, see section 6) |
| Whole GUI: labels, cursor card, auto-identification chip, follow card, side panel, message list | virtual-display runs with real recordings | pass; found and fixed several real problems (below) |
| Long use | 6 minutes of continuous following, then 15 follow/stop cycles | memory flat (about 244 MB); threads and descriptors back to baseline after each cycle; no leftover decoders |

## 4. Bugs the testing found (and fixed)

Listed because they show what the tests are good for:

* **A crash on unexpected data from a helper program** (found by the fuzz tests): a sensor or telemetry line whose JSON had
  a field of the wrong type (a number where text was expected) made the JSON library throw, and an uncaught exception on
  a reader thread terminates the whole app. All parsing of outside data is now exception-safe, over-long decoder log lines
  are cut before the (recursive) regular-expression matcher sees them, and absurdly deep JSON is not parsed. The fuzz
  tests (`test_fuzz`, about 58,000 checks, deterministic) throw random, mutated, truncated, huge, deeply nested and
  NaN / Inf input at the rigctl command parser, the decoder telemetry and log parsers, the evidence rules, the sensor-line
  summariser, the ADS-B frame decoder and the demodulator, and are clean under AddressSanitizer / UBSan / ThreadSanitizer.
* **Use-after-free on teardown**: a sample block delivered just after a channel was closed could reach a destroyed
  object. Invisible on Linux, crashed on macOS CI; confirmed with ThreadSanitizer (10 races before the fix, 0 after).
* **A data race in the trunk follower** (found by running the whole suite under ThreadSanitizer).
* **Follow started on the wrong channel** when an automatic background probe of another signal was still running (found in
  a long GUI soak; each identification result now carries the exact frequency it belongs to).
* **Retuning the radio by hand while following** left the hidden channels listening on the wrong frequency (SDR++ keeps a
  channel's offset, not its frequency). Channels are now re-pinned to their absolute frequency; if the window leaves the
  channel being followed, following pauses with an explanation, resumes by itself, and offers "Return to control channel"
  (`trunk_follower::user_moving_the_window_away_pauses_following_and_it_resumes`).
* **The cursor card pointed at the wrong signal** for VFOs whose reference is their edge (USB/LSB/RAW), because the
  VFO's reference point was used instead of its centre.
* **Endless re-testing**: a steady analog channel was re-probed every 90 s forever (several decoder processes each time);
  now backs off from 1.5 minutes up to an hour.
* **The "Identify signal under the cursor" button in the SDRstar panel crashed the app** (found driving the whole GUI): the
  code decided whether to call `endDisabled()` from state that the click itself had just changed, so ImGui's style stack
  was popped once too often. The condition is now evaluated once.
* **The SDRstar panel's settings were never saved** (found by restarting the GUI and looking at the file): the settings
  file was only ever written when the app created it, so every start began with the defaults. Auto-save is now on, and
  hidden tips are written immediately.
* **Decoded voice from the single-voice modes played at twice the pitch and speed**: DSD-neo writes P25 Phase 1, NXDN,
  D-STAR, YSF, dPMR, M17 and ProVoice as mono; SDRstar always read stereo. The earlier tests only counted audio frames
  and checked that they were not silence. Now `dsdOutputChannels()` knows each mode and the tests measure the pitch.
* **Choppy voice and a frozen app with two audio streams**: the audio callback of SDR++'s PortAudio sink waits for a
  whole block, with no buffering in front of it for SDRstar's 20 ms voice frames; and with the silent "SDRstar Voice" stream
  on the same device as the radio's, CoreAudio's single I/O thread was held up. See ARCHITECTURE.md, *Voice playback*.
* **Background work competed with the interface**: automatic identification starts several decoder processes at once,
  parsed every log line with up to eight regular expressions under the lock the interface polls, and re-read their logs
  every frame. Decoders now run at lower priority, the regular expressions only run on lines that can match and outside the
  lock, and the evidence is re-evaluated five times a second instead of every frame.
* **Detector design problems found with real recordings**: spectral flatness does not separate digital from analog
  (so no label is derived from it); a slow average missed bursts (instantaneous presence added); edge-of-band
  skirts looked like signals (edge guard added); the label said "control channel?" far too often (facts on the label,
  speculation in the note).
* **DSD-neo's own auto-detect was measured to guess wrong** for D-STAR, dPMR and CQPSK voice, so SDRstar tests specific
  decoders in parallel and claims a protocol only on error-checked evidence.
* Plus build / platform issues: `environ` not linkable from a macOS plug-in, GCC 13 `-Werror` in DSD-neo, SDR++'s
  File Source reading every WAV as 16-bit, and others.

Sanitizer caveat: the real-air test plays a recording against real-time deadlines, and at sanitizer speed its
identification step can miss its deadline (a timing failure, not a memory or race report: both sanitizers reported
nothing for it). CI therefore only fails on sanitizer *reports*.

## 5. Known weak spots (measured)

* **NXDN96 and dPMR** decode only weakly through the audio (FM discriminator) path SDRstar feeds the decoder, so they
  are identified less reliably than the other protocols. (Fixing this properly would need the complex-IQ path.)
* **DMR control channels in the real capture** decode mostly with CRC errors, so DMR trunk *semantics* were not verified
  beyond sync / colour code / short link control. DMR, NXDN and EDACS trunking were exercised with the decoder's own
  fixtures, not with a real multi-channel system.
* **TETRA, AIS, ACARS, DAB** are not decoded.
* **ADS-B needs a channel at least about 1.8 MHz wide** (so the 2.4 MS/s sample rate): measured on the real recording, 135 frames at 1.9 MHz, 122 at 1.8 MHz and none at 1.5 MHz, because the 0.5 microsecond pulses blur together. SDRstar says so when the sample rate is too low. The ADS-B decoder ignores other Mode S message types (altitude / identity replies), so it shows fewer messages than a full decoder would count.
* **Short recordings**: the real P25 capture is only about 4 seconds long, enough to decode the control channel and see real
  grants but short for long-running state machine behaviour.

## 6. What could not be tested here

* **The audio freeze and the audio smoothness on a real Mac**: the cause was found by reading SDR++'s sink code and
  confirmed in isolation (the unpatched ring-buffer read never returns on a silent stream), the voice path was run end to
  end on Linux (frames reach the audio thread at the right rate), but CoreAudio itself, and how the voice *sounds*, could
  not be run here.
* **A real RTL-SDR on a real Mac**: no hardware and no Mac were available. Untested: USB streaming, real retune latency,
  audio output device handling, the GUI's OpenGL window on a real display (GitHub's Mac runners have no usable window
  server, so CI only proves that every plug-in loads and a headless launch works).
* **Gatekeeper's first-launch dialog** on a downloaded copy (the instructions are in the install guide).
* **Anything depending on real antennas, real gain settings and real-world RF conditions.**

## 7. Running the tests yourself

```sh
cmake -S core -B build/core -DCMAKE_BUILD_TYPE=Release && cmake --build build/core
export SDRSTAR_DSD_NEO=/path/to/dsd-neo SDRSTAR_FIXTURES=/path/to/dsd-neo/tests/fixtures/iq
export SDRSTAR_MULTIMON=/path/to/multimon-ng SDRSTAR_RTL433=/path/to/rtl_433     # optional: text-decoder tests
tools/fetch_test_samples.sh                                                       # optional: the sensor capture
export SDRSTAR_REAL_SLICES=/path/with/the/three/p25_dmr_800mhz_hackrf_slice*/dirs   # optional: real-air trunk tests
(cd build/core && ctest --output-on-failure)
scripts/safety_audit.sh
```

Tests whose data or program is missing print "(skipped ...)" instead of failing; `scripts/test_core.sh` (used by CI)
turns a skip of the DSD-neo integration tests into a failure so a broken environment cannot pass silently.
